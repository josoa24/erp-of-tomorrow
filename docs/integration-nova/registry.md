## Module and adaptation keys (shared constants)
Base modules: `accueil`, `ventes`, `stock`, `equipe`, `relations`. Adaptations: `stock.lots-peremption`, `ventes.mobile-money-credit`, `relations.nif-plafond-credit`, `equipe.avances-salaire`. A module screen in Eclipse preview is opened by search param `eclipse=<adaptationKey>` (e.g. `/stock?eclipse=stock.lots-peremption`).

## Stock (owner I2) — base path /api/stock
- S1 Product `category` varchar(80) NULL and `purchasePrice` numeric(14,2) NULL: in Product create/update requests (optional), ProductResponse and StockStatusItem. `/summary` adds `availabilityRate` (0..1, products above threshold / total), `criticalLowStock` (lowStock && CRITICAL count), `totalPurchaseValue` (Σ qty × coalesce(purchasePrice, unitPrice)), `productsWithoutPurchasePrice`, `expiringSoon` (S3). Existing fields unchanged.
- S2 `/status` adds `search` (name/sku/category, case-insensitive) and returns per item `category`, `statusLabel` enum `RUPTURE_RISK | BELOW_THRESHOLD | IN_STOCK` (CRITICAL ⇒ RUPTURE_RISK; else lowStock ⇒ BELOW_THRESHOLD; else IN_STOCK) plus S3 fields. `GET /status/counts` -> `{all, alert, ruptureRisk, expiringSoon}` (alert = lowStock count, ruptureRisk = RUPTURE_RISK count).
- S3 Lots (adaptation stock.lots-peremption): table `stock_lots` (id PK, product_id FK products NOT NULL, movement_id FK stock_movements NOT NULL UNIQUE, lot_number varchar(64) NOT NULL, expiry_date date NOT NULL, quantity int NOT NULL CHECK > 0, received_at timestamptz NOT NULL; UNIQUE(product_id, lot_number)); table `stock_lot_allocations` (id PK, lot_id FK stock_lots NOT NULL, movement_id FK stock_movements NOT NULL, quantity int NOT NULL CHECK > 0). Both append-only (no updater/deleter). `POST /products/{id}/movements` accepts optional `lotNumber` + `expiryDate` (both or none, IN only, expiry >= today) -> creates the lot; every OUT movement allocates FEFO across lots with remaining > 0 (remaining = quantity − Σ allocations), quantity beyond lots is untracked stock. Status item fields: `lotNumber`, `expiryDate`, `daysToExpiry` of the earliest-expiring lot with remaining > 0 (null if none), `expiringSoon` = daysToExpiry <= `stock.expiry-alert-days` (30). `/status?expiringWithinDays=N` filter. `GET /products/{id}/lots` -> [{lotNumber, expiryDate, quantity, remaining, receivedAt}].
- S4 Purchase order quick draft for Accueil: existing `POST /purchase-orders` reused as is.

## Vente sales (owner I3) — base path /api/vente
- V1 SaleResponse gains `number` ("V-" + id zero-padded to 4), `customerName` (null customer ⇒ "Client comptoir"), `paymentMethod` (CASH | MVOLA | ORANGE_MONEY | AIRTEL_MONEY | CREDIT, null on legacy), `creditDays` (int, CREDIT only), `dueDate` (date: validated date + creditDays, validated date when not CREDIT), `paidAmount`, `paymentStatus` (DRAFT | TO_COLLECT | OVERDUE | PAID | CANCELLED), `toDeliver` (boolean). New columns on `sales`: payment_method varchar(20) NULL, credit_days int NULL, to_deliver boolean NOT NULL DEFAULT false. Set while DRAFT via create/update request (optional fields).
- V2 Payments: table `sale_payments` (id PK, sale_id FK sales NOT NULL, amount numeric(14,2) NOT NULL CHECK > 0, method varchar(20) NOT NULL, paid_at timestamptz NOT NULL, reference varchar(64) NULL, recorded_by bigint NULL), append-only. `POST /sales/{id}/payments {amount, method, reference?}` (VALIDATED, not cancelled, amount <= remaining else 422) -> 201; `GET /sales/{id}/payments`. Backfill migration: one CASH payment = total for every VALIDATED sale that has none (paid_at = validated_at), so history is "Payée".
- V3 Cancellation: table `sale_cancellations` (id PK, sale_id FK sales NOT NULL UNIQUE, reason varchar(500) NOT NULL, cancelled_by bigint NULL, created_at timestamptz NOT NULL). `POST /sales/{id}/cancel {reason}` (VALIDATED, no payment recorded, else 422) re-enters stock with one IN movement per line (reason "Annulation V-xxxx"), with compensation on failure -> 200.
- V4 `GET /sales` adds `search` (number, customer name), `paymentStatus`, `toDeliver`, `page`, `size` (X-Total-Count; without page/size: full list as today). `GET /sales/counts?from=&to=` -> `{all, toCollect, paid, cancelled, overdue, credit, draft}`. Default order createdAt desc.
- V5 `GET /sales/summary` unchanged + new `GET /sales/kpis` -> `{monthRevenue, previousMonthRevenue (same day-span of previous month), todaySalesCount, todayRevenue, todayCollected, sameWeekdayLastWeekRevenue, averageBasket, previousMonthAverageBasket}`; `GET /sales/credit-summary` -> `{outstanding, customers, overdueCustomers}`; `GET /sales/credit-by-customer` -> [{customerId, outstanding, overdueCount}] (non-cancelled CREDIT sales, outstanding = total − paid > 0).
- V6 Product catalog for VENTE role: `GET /catalog/products?search=` -> [{id, name, sku, unit, unitPrice, quantity}] proxied to stock-service with the caller's headers (VENTE cannot call /api/stock).

## Relations (owner I4)
- P1 vente customers: `nif` varchar(20) NULL, `stat` varchar(30) NULL, `creditLimit` numeric(14,2) NULL in requests/responses; `GET /customers` adds `type` filter.
- P2 stock suppliers: `city` varchar(80) NULL, `nif`, `stat` (same as P1) in requests/responses.
- P3 crm: `GET /contacts?kind=ALL|CUSTOMER|SUPPLIER&search=&followUp=&professional=` -> [{kind, partyId, name, initials, typeLabel ("Client · professionnel" | "Client · particulier" | "Fournisseur"), city, phone, lastInteractionAt, status ACTIVE|FOLLOW_UP, nif, stat, creditLimit, outstanding, overLimit}] sorted by lastInteractionAt desc nulls last; follow-up = max(lastInteraction, createdAt) older than `crm.follow-up-days` (30). `GET /contacts/counts` -> `{all, customers, suppliers, followUp, professional}`; `GET /contacts/summary` -> `{activeCustomers (distinct customers with VALIDATED sale since quarter start), totalCustomers, suppliers, openPurchaseOrders (VALIDATED not received), followUp, creditOutstanding, overLimitCustomers}`; `POST /contacts {kind, name, phone?, email?, city?, type?, nif?, stat?, creditLimit?}` forwards to vente `POST /customers` or stock `POST /suppliers` -> 201 contact. Existing interactions endpoints reused for "Enregistrer un échange".

## RH (owner I5) — base path /api/rh
- H1 Employee `contractType` (CDI | CDD | STAGE | JOURNALIER, column contract_type varchar(16) NULL), EmployeeResponse gains `departmentName`, `onLeaveToday` (boolean), `status` PRESENT | ON_LEAVE.
- H2 `GET /leaves` adds `activeOn` (date); LeaveResponse gains `employeeName`, `decidedBy`; `leave_requests.decided_by bigint NULL` filled from X-User-Id. `GET /summary` adds `pendingLeaves`, `departmentsWithEmployees`, `onLeaveToday` computed in Indian/Antananarivo; `GET /employees/counts` -> `{all, present, onLeave, advanceRequested}`.
- H3 Salary advances (adaptation equipe.avances-salaire): table `salary_advances` (id PK, employee_id FK employees NOT NULL, month date NOT NULL (first day), amount numeric(14,2) NOT NULL CHECK > 0, reason varchar(500) NULL, status varchar(16) NOT NULL (DRAFT|VALIDATED|REJECTED), created_at NOT NULL, decided_at NULL, decided_by bigint NULL). `GET /advances?month=&employeeId=&status=`, `POST /advances {employeeId, amount, reason?}` (current month; Σ DRAFT+VALIDATED of the month + amount <= baseSalary × `rh.advance.cap-percent` (30) else 422), `POST /advances/{id}/validate|reject` (ADMIN only via X-User-Role, 403 otherwise; re-check cap at validation; non-DRAFT -> 409 IMMUTABLE). EmployeeResponse gains `monthAdvance` (Σ DRAFT+VALIDATED current month), `monthAdvancePending` (boolean), `advanceCap` (baseSalary × 0.30). `GET /advances/summary` -> `{monthTotal, requests, pending}`. Employee deletion refused if advances exist.
- H4 Leaves validate/reject remain RH|ADMIN (unchanged).
